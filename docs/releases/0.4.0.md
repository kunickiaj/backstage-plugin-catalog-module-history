# `0.4.0` release

`0.4.0` adds opt-in scheduled retention, so retained history no longer has to grow without limit. It also stops the default store from opening a database connection when history is disabled, and adds a config-aware way to wrap entity providers. All five public packages were released as `0.4.0` with the `latest` dist-tag. The approved OIDC workflow run [40411906131](https://github.com/kunickiaj/backstage-plugin-catalog-module-history/actions/runs/40411906131) published them from `main` at `c573922d12e5515da77be93a2733833b75772c32`, and each package has a GitHub Actions provenance statement. No schema migration is added, and retention stays off until you enable it.

## Changes since `0.3.0`

- **Scheduled retention.** Set `catalog.history.retention.enabled: true` and a `maxAge` of at least 1 day to schedule the `catalog-history-retention` task on one backend replica. By default it runs every 24 hours with a 1 hour timeout and a 5 minute initial delay. Runs are dry runs until you set `dryRun: false`. They keep the newest row of each entity capture stream and delete in transactions of at most `batchSize` rows or cycles (default 1000). See [Retention](../../README.md#retention), [Plan retention](../sizing.md#plan-retention), and the [operations runbook](../operations.md).
- **Retention store methods.** `HistoryStore` gains optional `planRetention` and `applyRetention` methods, and `@kunickiaj/backstage-plugin-catalog-history-node` exports `HistoryRetentionRequest`, `HistoryRetentionCounts`, and `HistoryRetentionAbortedError`. The default PostgreSQL store implements both methods. Custom stores keep working and only need the methods if retention is enabled.
- **Retention metrics.** `catalog.history.storage.operation.duration` reports the `plan_retention` and `apply_retention` operations.
- **No database work while history is off.** The default `historyStoreServiceFactory` now opens its connection and runs migrations on first use rather than when the service is resolved. With `catalog.history.enabled: false`, the backend opens no history connection and runs no migrations. The same holds when the API, provider, processing, reconciler, and retention layers are all off. With any layer on, migrations still run at startup, so the default configuration still fails early on schema errors.
- **Config-aware provider wrapping.** `HistoryRecordingEntityProvider.fromConfig(config, { inner, store, logger })` records only when both `catalog.history.enabled` and `catalog.history.provider.enabled` are on. Otherwise it forwards mutations without touching the store. Every catalog module receives the same plugin-scoped store, so wrappers, processor capture, the reconciler, retention, and the read API share one connection.
- **Change-feed cursor after retention.** A change-feed request whose cursor points at a row removed by retention now returns `400` instead of an empty page that looked like the end of history. Clients start again from the first page.
- An [operations runbook](../operations.md) covers growth, failed migrations, reconciler and query timeouts, retention, permission errors, and turning layers off.

## Upgrade notes

Wrappers built from the earlier README example passed only `catalog.history.provider.enabled` to `HistoryRecordingEntityProvider`, so they kept recording after `catalog.history.enabled: false`. Switch to `HistoryRecordingEntityProvider.fromConfig` if the master switch should stop provider capture. The constructor and its `enabled` option are unchanged.

Retention deletes history permanently. Run it as a dry run first, check the logged counts, and take a backup before the first deleting run. PostgreSQL reuses freed space after vacuum, but the table files do not shrink on their own.

The [known deletion-capture limitation](../../README.md#known-deletion-capture-limitation) still applies.

## Compatibility

Dependencies are unchanged from `0.3.0`. All five packages support Node 22 and 24, and backend dependencies stay aligned with Backstage 1.56.2, for example `@backstage/backend-plugin-api` `^1.11.0` and `@backstage/plugin-catalog-node` `^2.2.6`. The frontend still targets NFS `0.18.2`, `@backstage/plugin-catalog-react` `3.3`, Backstage UI `0.19`, and React 18.
