# `0.2.0` release candidate

`0.2.0` prepares five packages for a coordinated public release. It is not published yet: the four backend-family packages remain on npm at `0.1.0`, and `@kunickiaj/backstage-plugin-catalog-history` has no npm release.

## Release contents

| Package                                                      | Release role                                      |
| ------------------------------------------------------------ | ------------------------------------------------- |
| `@kunickiaj/backstage-plugin-catalog-history-common`         | Shared contracts and permissions                  |
| `@kunickiaj/backstage-plugin-catalog-history-node`           | Backend service references and contracts          |
| `@kunickiaj/backstage-plugin-catalog-history-storage-node`   | Postgres storage and migrations                   |
| `@kunickiaj/backstage-plugin-catalog-backend-module-history` | Catalog backend module and read API               |
| `@kunickiaj/backstage-plugin-catalog-history`                | NFS frontend History tab and catalog-history page |

The candidate requires Node 22 or 24. Frontend E2E coverage uses NFS `0.18.2`, `@backstage/plugin-catalog-react` `3.3`, Backstage UI `0.19`, and React 18.

## Backend E2E setup

The module's default loader still includes the Postgres history store. Existing provider-wrapper wiring stays the same; add the wrapper where each provider is registered when provider-origin capture is needed.

Enable the read API:

```yaml
catalog:
  history:
    api:
      enabled: true
```

The routes require authenticated users and the `catalog-history.read` permission. When the permission framework is enabled, return an explicit `ALLOW`; global history access does not mirror live-catalog visibility and can include metadata for deleted entities.

Fresh schemas apply all three history migrations; existing development data applies pending migrations on startup. Back up data you need before testing an upgrade. The global-feed index builds during normal startup and can block history-entity writes on large retained histories, so plan a maintenance window before that deployment.

Processing capture does not observe deletes. Use provider capture or the reconciler when deletion coverage is part of the E2E scenario.

Garbage collection, retention limits, and large-history scale behavior are not part of this release's supported claims.

## Frontend E2E setup

Register the default plugin through the host application's existing NFS feature and discovery setup. Keep existing features; do not replace them or add a legacy Material UI route.

```ts
import { createApp } from '@backstage/frontend-defaults';
import catalogHistoryPlugin from '@kunickiaj/backstage-plugin-catalog-history';

export default createApp({
  features: [
    // Existing NFS features stay here.
    catalogHistoryPlugin,
  ],
});
```

Load the BUI stylesheet once if the host does not already do so:

```ts
import '@backstage/ui/css/styles.css';
```

The entity tab is scoped to the current catalog entity. The global page is `/catalog-history` and can show retained events for entities deleted from the live catalog.

For an update, field differences compare the saved current snapshot with the immediately preceding saved snapshot for the same entity, source, and provider. A delete has no deletion payload: the UI may show the prior saved state as **Last recorded snapshot before deletion**, which is not a deletion snapshot. If there is no comparable prior state, no field diff is available.

## Release validation and publication

Preparation of the `0.2.0` bootstrap tooling is approved; publication is not authorized yet. **bootstrap_frontend** defaults to unchecked. Run a validation-only workflow dispatch from the release branch with **publish** unchecked and **bootstrap_frontend** unchecked.

Merge the release PR only with explicit merge approval. A separately approved `main` dispatch then uses **publish** checked and **bootstrap_frontend** checked.

That bootstrap dispatch publishes the existing package names with GitHub Actions OIDC and provenance, then records the unpublished frontend archive as pending. Its final warning means `0.2.0` is not yet a completed five-package publication. A separately approved, personally authenticated npm action publishes the exact frontend archive from the same successful CI artifact; only then can its trusted publisher be configured.

The workflow packs through Yarn after typecheck and build, validates all archives, and publishes only those validated archives. It does not rebuild in the publishing job. After the frontend trusted publisher is configured, future releases use normal publication with **bootstrap_frontend** unchecked. See [Publishing packages](../publishing.md) for artifact verification, trust requirements, and recovery rules.
