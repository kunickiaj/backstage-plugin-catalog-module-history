# `0.5.0` release

`0.5.0` lets users compare any two recorded events of an entity, fixes history recording overlapping provider mutations out of order, and removes published contract surface that nothing implemented. All five public packages move to `0.5.0` together. No schema migration is added. **This release has breaking changes for code that imports moved symbols from the backend module or implements the query contract**; see [Breaking changes](#breaking-changes).

## Changes since `0.4.0`

- **Compare two recorded events.** `GET /api/catalog/history/entities/:kind/:namespace/:name/diff?from=row:<id>&to=row:<id>` returns how one recorded row became another, with both versions. In the History tab and the Catalog history page, select an event, choose **Compare with another event**, and select a second event of the same entity. The Catalog history page keeps the comparison in the URL, so the link can be shared. Comparisons across capture layers and with deletion records show an explanation. `HistoryStore.query.getEntityDiff` and `CatalogHistoryApi.getEntityDiff` are optional, so custom stores and APIs keep working; the route returns `501` and the UI hides the action without them. See [Compare two recorded events](../reference.md#compare-two-recorded-events).
- **Overlapping provider mutations are recorded in order.** When a provider called `applyMutation` again before an earlier call finished, for example a webhook push during a scheduled full refresh, history could record the older mutation last and end on an older version than the catalog. `HistoryRecordingEntityProvider` now records mutations in the order they reach the catalog. See [Upgrade notes](#upgrade-notes) for the behavior this changes.
- **Timeline paging no longer skips rows.** Entity timeline and version-list pages skipped rows that differed from the previous page's last row only in microseconds, which affected rows written by the column's `now()` default or imported data.
- **Stricter timestamps.** The default store now rejects impossible dates such as `2026-02-30` and offsets beyond ±15:59 with `InputError`, which the API returns as `400`. Before, PostgreSQL rejected them, and callers saw a database error or a `500`. `changedAfter`/`changedBefore` also compare fractions below one millisecond, as the cycle ranges already did. The common package exports the rule as `isHistoryInstant` and `compareHistoryInstants`.
- **History pickers behave the same.** The Provider picker gains the **Clear provider** button and "No matching providers." note the Entity and Kind pickers had, and reports loading while a search is pending. Reopening any picker reuses a successful search and retries a failed one.
- **One schema bootstrap per store.** The default store and its reads used to run schema bootstrap separately. They now share one.
- The [operations runbook](../operations.md) gains "Provider history is falling behind".

## Breaking changes

- **Removed re-exports from the backend module.** `@kunickiaj/backstage-plugin-catalog-backend-module-history` no longer re-exports `CaptureSource`, `CurrentEtag`, `CycleInput`, `EntityRow`, `HistoryStore`, `MutationType`, or `RECONCILER_PROVIDER` (import them from `@kunickiaj/backstage-plugin-catalog-history-node`), or `ensureSchema`, `historyStoreServiceFactory`, or `PostgresHistoryStore` (import them from `@kunickiaj/backstage-plugin-catalog-history-storage-node`). They have been deprecated since `0.2.0`. See [Removed compatibility re-exports](../../packages/catalog-backend-module-history/README.md#removed-compatibility-re-exports-in-050).
- **Removed unimplemented query contract.** `HistoryQueryService.getFacets` and `getStats` and their types (`HistoryFacetBucket`, `HistoryFacetsRequest`, `HistoryFacetsResponse`, `HistoryStatsRequest`, `HistoryStatsBucket`, `HistoryStatsResponse`) are removed. No store or route implemented them. Custom implementations can delete them.
- **Diff targets are rows only.** `HistoryDiffTarget` is now `{ kind: 'history-row'; id }`, and `HistoryEntityDiffRequest` no longer has `source` or `provider`. The `cycle` and `timestamp` kinds shipped in `0.4.0` types but every layer rejected them.

## Upgrade notes

- **Provider forwarding is now sequential per provider.** Overlapping `applyMutation` calls from one wrapped provider reach the catalog one at a time, in arrival order. They used to run in parallel. Without `convertFullToDelta`, catalog writes still never wait for history, but each call still resolves after its own recording. The wrapper logs `History recording for provider <name> is <n> mutations behind` when more than 20 recordings are queued.
- **With `convertFullToDelta` on, history gates that provider's catalog writes.** A converted full reads its history baseline before it forwards, so it waits for earlier recordings, and later writes wait for it. A history call that hangs stops that provider's catalog writes until it finishes. `catalog.history.api.queryTimeoutMs` does not cover these reads or recording writes.
- The [known deletion-capture limitation](../../README.md#known-deletion-capture-limitation) still applies.

## Compatibility

Dependencies are unchanged from `0.4.0`. All five packages support Node 22 and 24, and backend dependencies stay aligned with Backstage 1.56.2, for example `@backstage/backend-plugin-api` `^1.11.0` and `@backstage/plugin-catalog-node` `^2.2.6`. The frontend still targets NFS `0.18.2`, `@backstage/plugin-catalog-react` `3.3`, Backstage UI `0.19`, and React 18.
